# Phase E2 — 创建者转交

基线：#97 普通合并 `a6446759e00c786e507803e9183a79e4934e4ffe`。本分支独立，不续写 E1；只实现创建者转交。家庭产品入口仍默认关闭，`identityLoopAccepted` 不改。

## 操作契约

选中的家庭卡片 → 家庭成员。创建者对现有成员点「转交创建者」，确认后产生服务端待接受请求。对方打开家庭成员，点「接受转交」并再次确认，事务成功后才换角色。读取请求、重新登录或进入页面都不自动接受。

原创建者在待接受期间仍负责家庭，可以「撤销转交」。第一版每家仅一份待接受请求；未增加邀请推送、私信或自动到期规则。接任人离开、被移除、重新加入（membershipId 已变）、角色已改变或家庭解散时，旧请求不能继续；下一次读取／发起会将失效请求归档，不把旧请求改成新资格。

接受成功：原创建者为成员，接任人为创建者；未使用的旧邀请统一撤销，新创建者重新发邀请。已使用邀请不改；家庭历史分享、其他家庭、个人来源、生活册不改。旧创建者此后可以按 E1 离开家庭。

不涉及 StoreKit、订阅、收费责任或支付账户转移；确认文案明确说明。解散与一个月清理、账号删除、公开注册、生产部署均不在本阶段。

## 数据与并发

服务端新增 migration 22 `family_creator_transfers`，不修改迁移 1–21。family/fromUser/requestId 唯一，每家只有一份 pending；transferId + revision + 原／目标 membershipId 构成提交资格。

新建的同一意图重试返回原收据，不重复创建。已经接受／撤销的重试只返回收据，不再次交换角色。接受与撤销由 SQLite BEGIN IMMEDIATE 串行化。先降原角色，再升新角色；事务后任何一步失败全部回滚，不出现长期无创建者或两位创建者。

客户端用真实返回的 roster/transfer 绑定账号与会话，检查 focus、前台、本机保护、请求世代。失焦或切账号后的结果不更新界面、不接着发送下一步；已经发往服务器的写入可能完成，回来须重新读取确认，不假称已撤销服务器事务。忙碌锁由所属请求持有，重复点击不能重复提交。

成员称呼沿用 E1：你／创建者／成员 N 和加入日。尚无经确认的成员姓名，不暴露邮箱、手机号或内部 userId；正式面向真实家庭前须解决成员辨认问题。

## 本地测试准备

E2 无新原生依赖，同一 Dev Client 可使用本分支 Metro；需要重启使用本分支源码的隔离 API。`family-api` 的 SQLite 模式启动会应用 migration 22；也可先对**隔离文件**运行 `npm run family-api:migrate`。保留原隔离数据库与媒体目录，不清个人库、不写生产。

A 原创建者，B 当前成员；两台模拟器分别登录。确认中文和英文的长操作名可达，至少 48pt。页面使用已有固定字号、系统图标和纸色，不恢复系统字号竞态适配。

具体验收见 WALK.md。测试双／SQLite Jest 不代替设备走查。
